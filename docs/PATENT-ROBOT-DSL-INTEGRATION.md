# 【발명의 명칭】로봇 벤더 및 통신 표준별로 상이한 인터페이스를 외부 도메인 특화 언어(DSL)로 단일화하는 로봇 임무 기술 시스템 및 그 통합 방법

> **문서 성격**: 본 문서는 현재 작업 폴더의 참조 구현(reference implementation)인
> `robotdsl` 저장소(외부 텍스트 DSL + VDA 5050 v3.0.0 컴파일러 + 자연어/음성 에이전트)를
> 분석하여 도출한 특허 명세서 초안이다. 명세서 중 예시 코드, 표, 오류 메시지, 수치는
> 모두 해당 저장소의 실제 동작을 근거로 한다.
>
> **참조 구현 한 줄 요약**: `robotdsl`는 이동 로봇(AGV/AMR) 임무를 평문(plain text)으로
> 작성하는 외부 DSL이고, 이를 파싱·의미검증·하향변환(lowering)하여 VDA 5050 v3.0.0
> JSON 메시지를 생성하며, 자연어(한국어 음성 포함)를 동일 DSL로 변환하는
> 생성-검증-재시도 루프를 갖춘 통합 시스템이다.

---

## 1. 기술분야

【0001】본 발명은 복수의 이동 로봇 벤더 및 복수의 로봇 통신 표준(예: VDA 5050 v1.x/v2.x/v3.0.0,
MiR 인터페이스, OPC UA, 벤더 고유 REST/MQTT API)이 서로 상이한 메시지 구조·메타데이터
규칙·열거형·토픽 체계를 갖는 환경에서, 운영자가 벤더나 표준 버전에 무관하게 **단일한
기술 인터페이스**로 임무(mission)를 기술하고, 이를 각 표준에 맞는 메시지 집합으로
자동 변환하는 로봇 임무 기술 시스템 및 그 통합 방법에 관한 것이다.

【0002】보다 구체적으로, 본 발명은 (a) 외부 텍스트 도메인 특화 언어(external DSL)의
설계, (b) 표준의 강제 북키핑(bookkeeping) 필드를 배제한 표준 중립 중간 표현(AST),
(c) 의미 규칙 검증 계층, (d) 표준별 메타데이터를 자동 생성하는 하향변환(lowering) 계층,
(e) 공식 표준 스키마에 대한 스키마 검증 계층, (f) 교체 가능한 표준/벤더 어댑터 프로파일,
(g) 자연어·음성으로부터 검증 가능한 DSL을 생성하는 생성-검증-재시도 루프,
(h) 지도(map) 기반 접지(grounding) 및 주행 가능성 판정, (i) 3중 검증 게이트 및 독립
교차 검증을 조합한 시스템 통합 기술에 관한 것이다.

## 2. 배경기술(선행기술)

【0003】이동 로봇(AGV/AMR)을 관제하는 업계의 사실상 표준인 VDA 5050(VDMA)는
플릿 매니저와 로봇 사이에서 `order`, `instantActions`, `zoneSet`, `state`,
`visualization`, `connection`, `factsheet`, `responses` 메시지를 교환하며, MQTT 토픽은
`vda5050/v{주버전}/{manufacturer}/{serialNumber}/{서브토픽}` 형태를 갖는다. 그럼에도
불구하고 현장의 인터페이스 이질성은 다음 요인에서 발생한다.

【0004】**(1) 벤더별 상이성.** 동일 표준을 지원하더라도 벤더마다 지원 서브토픽,
액션 타입(actionType) 어휘, 좌표계·단위·허용편차 해석, 연결(connection) 상태 모델,
게이트웨이 API가 다르다. 참조 구현이 연동한 관제 게이트웨이는 예컨대 맵을
`{"mapId": ..., "nodes": {"RK-AM": {"x":..,"y":..}}, "edges": [{"from":..,"to":..}]}`
형태로 제공하고, 로봇 목록을 `GET /api/robots`로 제공하는 반면, 다른 벤더는 전혀 다른
스키마와 인증 방식(Bearer 토큰 등)을 사용한다.

【0005】**(2) 표준 버전별 파괴적 변화.** VDA 5050 v2에서 v3.0.0으로 오면서 다음의
파괴적 변화가 있었다. 헤더 식별자 `header`가 `headerId`로 개명되었고, 엣지 속성
`edge.rotationAllowed`가 의미가 반전된 `edge.reachOrientationBeforeEntering`으로
대체되었으며, `zoneSet` 메시지와 `zoneType` 어휘(`BLOCKED`, `LINE_GUIDED`, `RELEASE`,
`COORDINATED_REPLANNING`, `SPEED_LIMIT`, `ACTION`, `PRIORITY`, `PENALTY`, `DIRECTED`,
`BIDIRECTED`)가 신규 도입되었다. 또한 v3.0.0은 즉시액션(instant action)의
`blockingType` 열거형을 `NONE`만 허용하도록 축소하였다. 따라서 표준 버전이 바뀌면
메시지 작성 규칙 자체가 달라진다.

【0006】**(3) 사람이 직접 JSON을 작성하는 방식의 취약성.** 표준은 운영자가 알 필요가
없는 강제 북키핑을 요구한다. `headerId`(토픽별 1씩 증가), ISO 8601 밀리초
타임스탬프, `version`, 노드와 엣지가 공유하면서 노드는 짝수·엣지는 홀수가 되어야 하는
`sequenceId`, 메시지 내 고유해야 하는 `actionId`, 미명명 엣지의 `edgeId`, 맵 식별자
`mapId` 등이 그것이다. 이를 수동으로 기입하면 토픽별 카운터 불일치, 타임스탬프 형식
오류, `sequenceId` 패리티 붕괴, `actionId` 중복 등이 발생하고, 브로커(broker)는 이를
조용히 거부(silent rejection)하므로 운영자는 실패 원인을 늦게 인지한다.

【0007】**(4) 벤더 어댑터 방식의 N×M 문제.** 종래에는 벤더마다 별도의 어댑터 또는
매핑 코드를 작성하였다. 벤더 수를 N, 표준/버전 수를 M이라 하면 N×M 개의 변환 로직이
필요하고, 표준의 부분 개정(schema 수정, enum 추가, 필드 개명)마다 전 어댑터를
수정해야 한다.

【0008】**(5) 관제 게이트웨이와의 의미 불일치.** 일부 관제 게이트웨이는 수신한 주문에서
엣지 제약(최고속도, 높이 제한, 방향, 회전 속도, 궤적, 코리더 폭 등)과 엣지 액션을
버리고 자체적으로 엣지(`e1`, `e2`, ...)를 재구성한다. 또한 `zoneSet` 엔드포인트를
제공하지 않을 수 있다. 이 경우 기술 계층에서 지정한 제약이 로봇에 도달하지 못하는
데도, 명령은 "성공"한 것처럼 보인다.

【0009】**(6) 자연어 명령 생성의 검증 부재.** 대규모 언어 모델(LLM)에 자연어를
표준 JSON이나 스크립트로 변환시키는 방식은 문법 오류, 표준에 존재하지 않는 노드
식별자 환각(hallucination), 맵에 존재하지 않는 구간(hop)으로 이루어진 주행 불가 경로
생성 문제가 있다. 파서·의미검증·스키마 검증 게이트가 없으면 이러한 출력이 그대로
디스크에 기록되거나 로봇에 전달될 수 있다.

## 3. 선행기술의 문제점

【0010】상기 선행기술은 운영자가 벤더별·표준별 상이한 메시지 형식과 메타데이터 규칙을
각각 학습하고 직접 기입해야 하므로, 기술 인터페이스가 단일화되지 못하고 인적 오류와
유지보수 비용이 증대된다.

【0011】또한 표준의 버전 업그레이드 시 필드 개명, enum 축소, 신규 메시지 도입을 모든
벤더 어댑터에 반영해야 하며, 검증 게이트가 없어 잘못된 메시지가 브로커에 도달한 뒤에야
문제가 드러난다.

【0012】또한 자연어 기반 명령 생성은 맵 데이터에 접지(grounding)되지 않아 환각
식별자와 주행 불가 경로를 만들고, 생성 오류가 운영자에게 피드백되지 않아 모델이 같은
실수를 반복한다.

## 4. 해결하고자 하는 과제

【0013】본 발명은 하기 과제의 해결을 목적으로 한다.

【0014】제1 과제: 복수 벤더 및 복수 표준 버전에 대해 운영자가 동일한 기술 인터페이스를
사용할 수 있도록, 인터페이스 이질성을 흡수하는 외부 DSL 및 단일화 파이프라인을
제공하는 것이다.

【0015】제2 과제: 표준이 요구하는 강제 북키핑 필드를 자동 생성하여 운영자의 입력을
최소화하고, 표준 준수를 구조적으로 보장하는 것이다.

【0016】제3 과제: 의미 규칙 검증, 공식 스키마 검증, 독립 구현체에 의한 교차 검증의
다중 게이트를 두어, 잘못된 메시지가 브로커나 로봇에 도달하지 않도록 하는 것이다.

【0017】제4 과제: 자연어(음성 포함)로부터 검증 가능한 DSL을 생성하고, 지도 데이터에
기반한 접지 및 주행 가능성 판정을 통해 환각 식별자와 주행 불가 경로를 제거하는 것이다.

【0018】제5 과제: 대상 표준·버전·벤더 프로파일을 교체 가능한 구성요소로 분리하여,
신규 벤더 또는 신규 표준 버전 대응 시 DSL·검증·사용자 인터페이스를 재사용할 수 있게
하는 것이다.

## 5. 과제의 해결 수단

【0019】본 발명은 상기 과제를 해결하기 위해, 이하의 수단을 포함하는 로봇 임무 기술
시스템 및 그 통합 방법을 제공한다. 이하 수단은 참조 구현 `robotdsl`의 실제 모듈에
대응한다.

### 5.1 외부 텍스트 DSL(기술 인터페이스 단일화의 전면)

【0020】본 발명의 기술 인터페이스는 평문으로 작성되는 외부 텍스트 DSL이다. 상기 DSL은
하기 설계 원칙을 갖는다.

【0021】**(a) 예약어가 없는 따옴표 이름.** 로봇 식별자, 맵 식별자, 주문·존·노드·엣지·
액션 이름은 모두 큰따옴표 문자열이다. 따라서 `pumpenhaus_1`, `MONTAGE`, `plant-b/l1`,
`RK-AM` 같은 실제 식별자를 예약어 충돌 없이 사용할 수 있고, 공백·점·대시·슬래시를
포함할 수 있다. 이에 따라 식별자 공간이 벤더별로 달라도 언어 문법은 변하지 않는다.

【0022】**(b) 순서 자유 수식어(order-free modifiers).** 노드 수식어(`describe`,
`at (x, y)`, `at (x, y, theta)`, `facing θ`, `on map <id>`, `deviation (a, b, theta)`,
`deviation_theta <rad>`)와 엣지 수식어(`describe`, `speed`, `maxheight`, `minloadheight`,
`orientation`, `orientation_type global|tangential`, `direction`, `reachbefore`,
`maxrotation`, `trajectory`, `length`, `corridor`) 및 액션 수식어(`blocking
none|soft|single|hard`, `describe`, `retriable`, `with { key = value, ... }`)는 임의의
순서로 기입할 수 있다. 운영자가 절 순서를 암기할 필요가 없으므로, 표준이 규정하는
필드 배치 순서와 무관하게 기술할 수 있다.

【0023】**(c) 식별자 경계에서 종료하는 대소문자 무관 키워드.** 키워드는 대소문자를
구분하지 않으며(`NODE`와 `node`는 동일), 반드시 식별자 경계에서 종료하므로 `speed`와
`speed_limit`이 충돌하지 않는다.

【0024】**(d) 주석 3종.** `#`, `--`, `/* ... */`를 지원하여 기존 운영 문서의 규칙을
그대로 인용할 수 있다.

【0025】**(e) 축약(sugar)과 세그먼트 추상화.** `go to "<node>" ... via "<edgeId>"`는
엣지 후속 노드의 축약이며, 파서 단계에서 명시적 스텝으로 전개되어 하류 계층은 하나의
형상만 본다. 주문 본문은 `route`/`base`(=`released: true`)와 `horizon`(=
`released: false`) 세그먼트로 구분되며, 세그먼트 키워드를 생략하면 전부 `base`로
취급한다.

【0026】**(f) 표준 어휘의 DSL 측 투영.** 존(zoneset)은 표준의 10종 `zoneType` 어휘를
DSL 키워드로 1:1 투영한다. 예컨대 `blocked` → `BLOCKED`, `speed_limit 0.25` →
`SPEED_LIMIT` + `maximumSpeed`, `priority factor 0.8` → `PRIORITY` +
`priorityFactor`, `directed heading 0.0 strictness restricted` → `DIRECTED` +
`direction` + `limitation: RESTRICTED`에 대응한다. 표준에 어휘가 추가되면 DSL 측
키워드와 하향변환 규칙만 추가하면 되므로, 언어 자체는 안정적으로 유지된다.

### 5.2 표준 중립 중간 표현(AST) — 표준 북키핑의 분리

【0027】본 발명의 중간 표현(AST)은 표면 문법에 충분히 가깝게 유지하되, **표준이
요구하는 북키핑 필드를 의도적으로 포함하지 않는다.** 즉 `sequenceId`, `actionId`,
`headerId`, `timestamp`, `version`은 AST에 존재하지 않고, 선택 가능한 항목은 전부
`Maybe`(옵션)로 표현되며 어떤 기본값도 부여되지 않는다.

【0028】이에 따라 (i) 파싱 계층과 하향변환 계층의 책임이 분리되고, (ii) 동일 AST를
서로 다른 표준 버전·벤더로 하향변환할 수 있으며, (iii) 표준이 필드를 추가하더라도
변경 지점이 하향변환 계층에 국소화된다.

【0029】또한 본 발명의 AST는 표준의 고정 어휘에 대해 **닫힌(closed) 생성자 집합**을
사용한다. 예컨대 존 종류는 `ZkBlocked | ZkLineGuided | ZkRelease |
ZkCoordinatedReplanning | ZkSpeedLimit | ZkAction | ZkPriority | ZkPenalty |
ZkDirected | ZkBidirected`로 한정되고, 각 생성자는 자신에게만 유효한 페이로드를
갖는다. 따라서 "`BLOCKED` 존이 `maximumSpeed`를 갖는" 것과 같은 무효 상태를 **표현
자체가 불가능**한 타입으로 만든다. 차단(blocking) 타입 역시
`BtNone | BtSoft | BtSingle | BtHard`의 닫힌 집합이다.

### 5.3 의미 검증 계층(문맥 의존 규칙의 중앙 집중)

【0030】본 발명은 파싱 다음에, 하향변환 이전에 **의미 검증 계층**을 둔다. 상기 계층은
표준의 서술형 규칙 중 잘못 기입하기 쉬워 브로커가 조용히 거부하는 규칙을 한 곳에서
검사하고, 실행 가능한 메시지(무엇을 고쳐야 하는지)를 산출한다. 참조 구현에서
검사하는 규칙은 다음과 같다.

| 규칙 | 내용 |
|---|---|
| 즉시액션 차단 타입 | 즉시액션(instant action)의 `blockingType`은 반드시 `NONE`. 오류 메시지 예시는 실시예 4(9.4절) 참조 |
| 폴리곤 정점 수 | 존 폴리곤은 최소 3개 정점. 오류 메시지 예시는 실시예 4(9.4절) 참조 |
| 팩터 범위 | `PRIORITY`/`PENALTY` 팩터는 `[0.0, 1.0]` |
| 각도 범위 | `theta`, `direction`은 `[-PI, PI]` 라디안 |
| 주문 갱신 식별자 | `orderUpdateId`는 비음수 정수 |
| 경로 교대 규칙 | 주문은 노드로 시작하고 노드·엣지·노드가 교대. 오류 메시지 예시는 실시예 4(9.4절) 참조 |
| 맵 식별자 해석 | 위치를 갖는 노드와 존셋은 `mapId`를 해석할 수 있어야 함(파일 상단 `map`, 노드의 `on map`, 존셋의 `on map` 중 하나) |
| 메시지 존재 | 주문·즉시액션·존셋 중 최소 1개 이상 |
| 수신자 존재 | `robot <manufacturer> <serialNumber>` 또는 CLI 기본값이 필요 |

【0031】본 발명의 의미 검증 계층은 **모든 문제를 한 번에 수집**한다(각 문제를 하나의
`Issue`로, 주체·메시지로 구성). 따라서 운영자는 한 줄 고치고 다시 실행하는 과정을
반복하지 않으며, 자연어 생성 루프에서도 하나의 시도로 모든 오류 사유를 피드백할 수
있다.

### 5.4 하향변환(lowering) 계층 — 표준 북키핑 자동 생성

【0032】본 발명의 하향변환 계층은 언어가 운영자에게 요구하지 않는 모든 표준 필수
북키핑을 생성한다. 참조 구현의 생성 규칙은 다음과 같다.

| 필드 | 생성 규칙 | 기술적 효과 |
|---|---|---|
| `headerId` | 토픽(메시지 종류)별로 독립 카운터를 두어 할당하고, 메시지마다 1 증가 | 동일 파일 내 두 주문은 연속 id, 같은 파일의 존셋은 같은 기준값에서 다시 시작 → 표준의 토픽별 의미 준수 |
| `timestamp` | ISO 8601 밀리초 포함 UTC(`YYYY-MM-DDTHH:MM:SS.fffZ`), 파일에 고정값이 있으면 그것을 사용 | 형식 오류 및 시계 불일치 제거, 재현 가능한 빌드 |
| `version` | 컴파일러가 대상으로 핀닝한 프로토콜 버전(참조 구현: `3.0.0`) | 버전 불일치 거부 |
| `sequenceId` | 노드와 엣지가 **공유**하는 순회 인덱스. 노드는 짝수, 엣지는 홀수, 세그먼트(base/horizon)를 넘어 연속 증가 | 표준의 갱신(updatability) 전제조건 충족 |
| `actionId` | 액션 타입의 슬러그 + 메시지 내 카운터(예: `init position` → `init-position-1`). 소스가 같으면 항상 동일 | 메시지 내 고유성 + 실행 간 안정성(재현성, diff 가능) |
| `edgeId` | 운영자가 명명하지 않으면 `edge-<sequenceId>` 합성 | 식별자 누락 방지 |
| `mapId` | 파일 상단 `map` 선언을 상속하고, 노드별 `on map`으로 재정의 | 맵 특정 실패 방지 |
| `blockingType` | 주문 액션은 `HARD`(표준 기본값), 즉시액션·존 액션은 `NONE` | v3.0.0의 즉시액션 enum 축소와 같은 버전별 규칙 흡수 |
| MQTT 토픽 경로 | `vda5050/v{주버전}/{manufacturer}/{serialNumber}/{서브토픽}` 자동 생성 및 출력 시 병기 | 발행 즉시 사용 가능한 토픽 확보 |

【0033】본 발명의 하향변환 계층은 **소스를 재해석하지 않는다.** 프로그램이 지정한
`blockingType`은 그대로 방출한다. 문맥 의존 규칙은 의미 검증 계층이 먼저 수행하므로,
하향변환은 순수한 결정적 변환으로 유지되고 테스트와 재현성이 확보된다.

【0034】또한 본 발명은 **우선순위가 명확한 문맥 해석 규칙**을 갖는다. 헤더
선언값(파일의 `header`, `timestamp`, `version`, `map`)이 CLI 기본값을 덮어쓰고, 파일이
명시하지 않은 항목만 문맥이 채운다. "파일은 자기 메시지의 주인"이라는 원칙에 따라,
설정 파일에 `header 42`를 고정하면 `--header-id 7`을 주어도 42가 사용된다.

### 5.5 스키마 검증 계층 — 공식 표준 스키마에 대한 최종 방어선

【0035】본 발명은 의미 검증 이후, 출력 이전에 **공식 표준 JSON Schema**에 대한 검증
계층을 둔다. 참조 구현은 JSON Schema draft 2020-12의 부분집합 검증기를 내장하여,
벤더링된 8개 공식 스키마(`order`, `instantActions`, `zoneSet`, `state`,
`visualization`, `connection`, `factsheet`, `responses`)를 외부 검증기 의존 없이
적용한다.

【0036】상기 검증기가 구현하는 키워드 부분집합은 `type`, `required`, `properties`,
`items`, `enum`, `const`, `minimum`, `maximum`, `exclusiveMinimum`, `minItems`,
`allOf`, `if`/`then`/`else`, 지역 `$ref`(`#/definitions/...`), `format: date-time`
이다. 위반은 JSON 포인터 경로(예: `/nodes/0/nodePosition/theta`)와 함께 보고된다.

【0037】핵심적으로, 본 발명은 **어떤 검증 계층이라도 실패하면 메시지를 기록하거나
출력하지 않는다.** 따라서 잘못된 메시지가 브로커에 도달하는 경로가 구조적으로
차단된다.

【0038】본 발명은 또한 표준 문서 자체의 결함을 흡수한다. 참조 구현이 직면한 실제
사례는 다음과 같다. (i) 공식 `zoneSet.schema`는 속성 정의명을 `"priorityFactor "`(후행
공백 포함)로 쓰면서 `required` 목록에는 `priorityFactor`를 사용한다. 하향변환 계층은
스키마가 실제로 검사하는 깨끗한 이름을 방출한다. (ii) 공식 스키마 3개 파일에 후행
쉼표 구문 오류가 있어, 참조 구현은 수리된 사본을 벤더링한다. 즉, 본 발명의 스키마
검증 계층은 표준의 서술과 실제 검사 동작 사이의 불일치를 **흡수하는 적응 계층**으로
기능한다.

### 5.6 교체 가능한 표준/벤더 어댑터 프로파일(N×M → N+M)

【0039】본 발명은 대상 표준을 **프로파일(profile)** 로 분리한다. 프로파일은
(i) 프로토콜 버전 식별자, (ii) 스키마 세트의 위치, (iii) 토픽/주소 체계,
(iv) 하향변환 규칙(북키핑 생성 규칙 및 필드명), (v) 의미 검증 규칙 세트으로 구성된다.

【0040】참조 구현에서는 프로토콜 버전과 토픽 레이아웃이 단일 모듈에 핀닝되고
(`ProtocolVersion`과 `topicPath`), 스키마 디렉터리가 CLI 옵션(`--schema-dir`)으로
지정되며, 메시지 종류별 스키마 파일명이 결정론적으로 매핑된다. 즉 버전 이동 시
변경 지점이 한 곳이다.

【0041】따라서 신규 표준 버전 또는 신규 벤더 인터페이스에 대응할 때, DSL 문법·의미
검증·생성 루프·사용자 인터페이스는 그대로 재사용하고 프로파일과 그에 따른
하향변환 규칙만 추가하면 된다. 이는 종래의 벤더별 어댑터 N×M 문제를 N+M으로
축소한다.

### 5.7 자연어·음성 → DSL 생성 루프(검증 게이트 내장)

【0042】본 발명은 운영자의 자연어 요청(한국어 음성 포함)을 DSL로 변환하는
**생성-검증-재시도 루프**를 포함한다. 상기 루프의 핵심은 "모델은 번역자일 뿐"이라는
안전 속성이며, 파서와 의미 검증이 모두 수용할 때만 결과가 운영자에게 도달하고
디스크에 기록된다.

【0043】상기 루프의 단계는 다음과 같다.

1. **프롬프트 구성.** 시스템 프롬프트는 (i) 출력 규칙("마크다운 코드 울리·설명·인사·
   질문 없이 소스만"), (ii) 문법 전체 레퍼런스(파서가 실제로 수용하는 모든 키워드),
   (iii) 지도 어휘(맵 식별자, 노드 id 목록, 엣지 id 목록, 주행 가능 홉 목록, 운용자가
   제한한 범위), (iv) 대상 로봇 식별자와 상태(오프라인/주행 중/대기), (v) "쉽게 틀리는
   규칙" 11개(이름은 항상 따옴표, 주문은 노드로 시작 후 교대, `sequenceId`·`actionId`·
   `headerId`·`timestamp`를 쓰지 말 것, 주문 액션 기본 `HARD`·즉시·존 액션은 `NONE`,
   위치가 있는 노드는 맵 필요, 폴리곤 3정점 및 액션 존의 3그룹 필수, 각도는
   `[-PI, PI]`, 팩터는 `[0, 1]`, `go to` 선호, 액션 타입은 표준 목록에서, 맵에 존재하는
   홉만 사용), (vi) 2개의 few-shot 예시로 구성된다.
2. **출력 정제.** 모델 출력에서 마크다운 코드 울리(선·후행), 첫 실제 선언 키워드 이전의
   서술문(prose)을 제거한다. 이는 포장(packaging)만 제거하며, 파서가 유효성의
   권위자로 남는다.
3. **생성.** 언어 모델에게 요청하여 DSL 소스를 얻는다.
4. **파싱.** 파서가 형상을 검사하고 줄·열 정보를 포함한 오류를 산출한다.
5. **선언 주입.** 생성된 소스에 `robot`/`map` 선언이 없으면 설정된 문맥에서
   주입한다(주입은 파싱 후, 의미 검증 전에 수행되어 주입된 선언 자체도 검증된다).
   모델이 단순히 잊은 경우와 운영자의 요청과 무관한 이유로 실패하는 것을 구분하기
   위한 것이다.
6. **의미 검증 및 하향변환.** 의미 검증 통과 시 하향변환하여 메시지를 생성한다.
7. **주행 가능성 판정(맵 거부).** 파싱·의미 검증을 통과했더라도, 지도가 해당 경로를
   수용할 수 없으면 재시도한다. 즉 두 노드 사이에 맵이 연결하지 않는 구간이 있으면
   "주행 불가"로 본다. 이 검사는 수동 저장을 게이트하지는 않는다(운영자가 초안을
   작성하는 동안에는 기록할 수 있어야 하므로), 생성 루프의 게이트로만 동작한다.
8. **피드백 및 재시도.** 거부 사유를 모델에 그대로 전달하여 수정을 요청한다. 파서
   오류는 줄·열 정보를 포함한 원문 그대로 피드백된다. 최대 3회.
9. **이력 관리.** 실패한 중간 시도는 대화 이력에 기록하지 않는다. 오직 검증을 통과한
   출력만 이력에 남으므로, 모델이 자신의 실수를 학습·재현하지 않는다.
10. **토큰 사용량 집계.** 모든 시도의 프롬프트·완료 토큰 수를 집계하여 보고한다.

【0044】본 발명의 생성 루프는 생성된 소스가 주행 불가 경로를 포함할 때 **거부 사유를
운영자에게 보이는 것과 동일한 문장**으로 모델에 전달한다. 예컨대 맵이 `RK-AM`을
`RK-AE`, `RK-AW`에만 연결하는 상황에서 `RK-AM -> CONV-OUT`을 생성하면,
`there is no edge from RK-AM to CONV-OUT; from RK-AM the map connects only to
RK-AE, RK-AW, so travel through those nodes`가 피드백된다. 이는 모델과 운영자가 같은
문장을 보게 하여 드리프트를 방지한다.

### 5.8 지도 기반 접지(grounding) 및 프리뷰

【0045】본 발명은 관제 시스템의 지도 데이터로부터 **어휘(vocabulary)**를 추출하여
생성기와 검증기의 근거로 사용한다. 어휘는 맵 식별자, 노드 식별자 목록, 엣지 식별자
목록, 주행 가능 홉(from, to) 목록, 노드 좌표, 운용자가 선택한 노드 부분집합(범위)으로
구성된다.

【0046】어휘 추출은 벤더별 지도 서술 형식의 이질성을 흡수하도록 **복수 형상을
허용**한다. 노드는 id를 키로 하는 객체 맵(`{"RK-AM": {"x":..,"y":..}}`) 형상, 엣지는
id를 키로 하는 객체 맵 형상 또는 `edgeId`를 포함하는 배열 형상을 모두 수용한다.
좌표가 없거나 숫자가 아닌 노드는 원점에 잘못 배치하지 않고 **제외**한다.

【0047】본 발명은 또한 **미리보기(preview)** 계층을 포함한다. 미리보기는 방출된
주문을 그 지도 위에 배치하여 (i) 이동 순서와 각 노드의 좌표, (ii) 인접 노드 쌍(홉)
목록, (iii) 각 노드의 `released` 여부(base/horizon), (iv) 지도가 모르는 노드와 홉,
(v) 관제 게이트웨이가 표현하지 못하는 구성(존셋 미전달, 엣지 제약·액션 유실)에 대한
경고, (vi) 역행(backtracking) 징후를 보고한다.

【0048】역행 탐지는 "동일 노드를 두 번 이상 방문"하는 사실을 보고하는 데 그치며,
최단 경로를 계산하여 정답과 비교하지 않는다. 우회가 의도된 임무일 수 있으므로 판단을
운영자에게 남기는 것이다. 이 보고는 운영자뿐 아니라 생성 루프에도 전달되어 모델이
경로 계획 실패를 수정하게 한다.

### 5.9 통합 서버 및 사용자 인터페이스

【0049】본 발명은 상기 파이프라인을 단일 서버 애플리케이션으로 통합한다. 참조 구현의
서버는 하기 라우트를 갖는 얇은(thin) 웹 애플리케이션이다.

| 라우트 | 목적 |
|---|---|
| `POST /api/command` | 텍스트 요청을 DSL로 생성(세션별 대화 문맥 유지) |
| `POST /api/listen` | 한 번의 발화를 음성 인식(STT)하여 텍스트로 변환 |
| `POST /api/compile` | 브라우저에서 편집된 DSL을 재컴파일 |
| `POST /api/save` | 재검증 후 파일 저장 |
| `POST /api/reset` | 대화 초기화 |
| `GET /api/context` | 사용 중인 어휘·로봇 목록·식별자·모델·버전 조회 |

【0050】서버는 DSL을 산출하는 모든 요청을 생성 루프를 통과시킨다. 따라서 잘못된
생성 결과가 저장되거나 유효한 것처럼 표시될 수 없다.

【0051】본 발명의 서버는 또한 **지도를 요청마다 재조회**한다. 기존에는 기동 시 한 번
읽어, 게이트웨이보다 늦게 뜬 에이전트가 영구적으로 맵 없이 동작하고 운영자가 원인을
구분하지 못하는 문제가 있었다. 재조회에 실패하면 이전 어휘를 유지하면서 오류를
보고하므로, 게이트웨이의 일시적 이상이 노드 식별자를 잃게 만들지 않는다.

【0052】본 발명의 사용자 인터페이스는 빌드 단계가 없는 브라우저 UI로서, 지도 위 경로
시각화, 예시 명령 선택, 음성 입력, 패널 기반 결과 표시를 제공하고, 브라우저 자동화
테스트(Playwright)로 검증된다. 플릿 의존 검사는 플릿이 없을 때 실패가 아닌 **건너뜀**
으로 처리되어, 맵 단독 실행도 지원된다.

【0053】음성 입력은 macOS Speech 프레임워크 기반 온디바이스 헬퍼(Swift)로 구현되어,
음성이 외부로 전송되지 않고 텍스트로 변환된 후 상기 생성 루프에 입력된다.

### 5.10 다중 게이트 및 독립 교차 검증

【0054】본 발명의 파이프라인은 다음의 게이트를 순서대로 통과해야만 출력된다.

1. **파싱 게이트** — 형상(문법) 검사, 줄·열 보고.
2. **의미 검증 게이트** — 표준의 문맥 의존 규칙 검사, 모든 문제 수집.
3. **스키마 검증 게이트** — 공식 JSON Schema 대조, JSON 포인터 경로 보고.
4. **(생성 경로 한정) 주행 가능성 게이트** — 지도 홉 기반 경로 수용성 판정.
5. **독립 교차 검증** — 출력 디렉터리에 대해 **별도 구현체**로 핵심 불변량을 재검사.

【0055】독립 교차 검증은 상기 파이프라인과 다른 언어·다른 구현으로 동일 불변량을
검증한다. 참조 구현의 교차 검증기는 필수 필드 존재, `sequenceId` 짝/홀 규칙,
`blockingType` 열거형, `zoneType`별 페이로드 요구사항, `actionId` 고유성, ISO 8601
밀리초 타임스탬프 형상, v2 필드명 부재 등을 검사하며 첫 위반에서 0이 아닌 종료 코드를
반환하여 CI에 그대로 투입된다(참조 구현 기준 274건 검사).

【0056】본 발명의 테스트 체계는 참조 구현 기준 파싱(키워드 경계 충돌 방지, 전
`zoneType` 파싱 포함), 방출(`sequenceId` 패리티, `actionId` 고유성·안정성, `headerId`
할당, `mapId` 상속, `priorityFactor` 키), 스키마 검증(모든 예제의 실제 스키마
라운드트립 및 검증기가 실제로 거부하는지 입증하는 부정 사례), 플릿 클라이언트, 맵
미리보기, 생성 루프, HTTP 표면을 포괄하는 105개 단위 테스트 케이스와 브라우저
자동화 테스트를 포함한다.

## 6. 발명의 효과

【0057】본 발명에 따르면, 운영자는 로봇 벤더나 표준 버전과 무관하게 **동일한 평문
인터페이스**로 임무를 기술할 수 있다. 예약어 없는 따옴표 이름과 순서 자유 수식어는
벤더별 식별자·필드 배치 차이를 흡수하고, 세그먼트·존·즉시액션 추상화는 표준 어휘의
버전별 변화를 흡수한다.

【0058】본 발명에 따르면, 표준의 강제 북키핑이 자동 생성되므로 운영자 입력량이
크게 감소하고, `headerId` 토픽별 할당, `sequenceId` 패리티, `actionId` 고유성·안정성,
타임스탬프 형식, 버전 핀닝이 구조적으로 보장된다.

【0059】본 발명에 따르면, 의미 검증·스키마 검증·독립 교차 검증의 다중 게이트로
인해 잘못된 메시지가 브로커나 로봇에 도달하지 않으며, 오류는 줄·열 또는 JSON 포인터
경로와 함께 실행 가능한 문장으로 보고된다.

【0060】본 발명에 따르면, 자연어·음성 인터페이스와 지도 기반 접지가 결합되어
비전문 운영자도 임무를 기술할 수 있고, 환각 식별자와 주행 불가 경로가 생성 단계에서
피드백·재시도로 제거된다.

【0061】본 발명에 따르면, 대상 표준·벤더 프로파일의 분리로 신규 표준 버전이나 신규
벤더 대응 비용이 N×M에서 N+M 수준으로 감소하고, 언어·검증·UI는 재사용된다.

【0062】본 발명에 따르면, 미리보기와 경고 계층을 통해 관제 게이트웨이가 실제로
버리는 구성(엣지 제약·액션, 존셋)을 사전에 인지할 수 있어, 명령이 성공한 것처럼
보이는 의미 불일치를 방지한다.

## 7. 도면의 간단한 설명

【0063】

- **도 1** 은 본 발명에 따른 로봇 임무 기술 시스템의 전체 구성도로서, 운영자(텍스트·
  음성), 웹 사용자 인터페이스, 통합 서버, 자연어 생성 루프, 외부 DSL 소스,
  파싱·의미검증·하향변환·스키마검증 파이프라인, 표준/벤더 어댑터 프로파일, 및 복수
  로봇 벤더·표준 버전으로의 출력 관계를 나타낸다.
- **도 2** 는 DSL 소스로부터 표준 메시지까지의 파이프라인 상세도로서, 표준 북키핑이
  AST에서 제거되고 하향변환 계층에서 생성되는 구조, 및 문맥 우선순위(파일 선언 >
  CLI 기본값 > 컴파일러 기본값)를 나타낸다.
- **도 3** 은 자연어 생성 루프의 시퀀스도로서, 프롬프트 구성 → 출력 정제 → 파싱 →
  선언 주입 → 의미 검증 → 하향변환 → 주행 가능성 판정 → 피드백·재시도(최대 3회) →
  이력 기록의 흐름과, 실패 시도가 이력에 기록되지 않는 점을 나타낸다.
- **도 4** 는 지도 기반 접지 및 미리보기 동작도로서, 지도 데이터로부터 어휘(노드·
  엣지·홉·좌표·범위)를 추출하고, 경로의 홉을 맵과 대조하여 미배치 노드·미연결 홉·
  역행·유실 구성을 보고하는 흐름을 나타낸다.
- **도 5** 는 다중 검증 게이트도로서, 파싱 게이트 → 의미 검증 게이트 → 스키마 검증
  게이트 → (생성 경로) 주행 가능성 게이트 → 독립 교차 검증의 순서와, 어느 한
  게이트라도 실패하면 출력되지 않는 구조를 나타낸다.

## 8. 특허청구범위

【0064】

### 독립항

**【청구항 1】** 복수의 로봇 벤더 및 복수의 로봇 통신 표준 버전에 대하여 단일한 기술
인터페이스를 제공하는 로봇 임무 기술 방법으로서,

운영자 단말로부터 외부 텍스트 도메인 특화 언어(DSL)로 작성된 임무 기술 소스를
수신하는 단계;

상기 소스를 파싱하여, 상기 표준이 요구하는 북키핑(bookkeeping) 필드를 포함하지
않고 선택 가능한 항목만 옵션으로 표현되는 표준 중립 중간 표현(AST)을 생성하는 단계;

상기 AST를 의미 규칙에 대하여 검증하는 단계로서, 상기 의미 규칙은 즉시액션의
차단(blocking) 타입이 사전 정의된 값이어야 한다는 규칙, 경로의 노드·엣지 교대 규칙,
및 폴리곤 정점 수 규칙 중 적어도 하나를 포함하는, 의미 검증 단계;

상기 검증된 AST를 하향변환(lowering)하여, 제1 로봇 통신 표준의 메시지 집합을
생성하는 단계로서, 상기 하향변환 단계는 상기 AST에 존재하지 않는 상기 제1 표준의
필수 북키핑 필드로서, 메시지 종류별로 독립적으로 할당되고 메시지마다 증가하는 헤더
식별자, 노드와 엣지가 공유하는 순회 인덱스로서 노드에는 짝수·엣지에는 홀수가
부여되는 순서 식별자, 및 액션 타입으로부터 유도되어 메시지 내에서 고유한 액션
식별자를 생성하는 단계; 및

상기 생성된 메시지 집합을 상기 제1 표준의 공식 스키마에 대하여 검증하고, 상기
검증을 통과한 메시지만을 출력하는 단계;

를 포함하는 것을 특징으로 하는 로봇 임무 기술 방법.

**【청구항 2】** 로봇 임무 기술 시스템으로서,

외부 텍스트 도메인 특화 언어(DSL)로 작성된 임무 기술 소스를 수신하는 수신부;

상기 소스를 파싱하여, 표준이 요구하는 북키핑 필드를 포함하지 않고 선택 가능한
항목만 옵션으로 표현되는 표준 중립 중간 표현(AST)을 생성하는 파서;

상기 AST를 의미 규칙에 대하여 검증하는 의미 검증부로서, 상기 의미 규칙은 즉시액션의
차단 타입 규칙, 노드·엣지 교대 규칙 및 폴리곤 정점 수 규칙 중 적어도 하나를
포함하는, 의미 검증부;

상기 검증된 AST를 하향변환하여 제1 로봇 통신 표준의 메시지 집합을 생성하는
하향변환부로서, 상기 표준의 필수 북키핑 필드를 생성하고, 상기 제1 표준의 프로토콜
버전, 스키마 세트 위치, 토픽 체계 및 하향변환 규칙을 교체 가능한 프로파일로
수용하는, 하향변환부; 및

상기 생성된 메시지 집합을 상기 제1 표준의 공식 스키마에 대하여 검증하고, 통과한
메시지만을 출력하는 스키마 검증부 및 출력부;

를 포함하는 것을 특징으로 하는 로봇 임무 기술 시스템.

**【청구항 3】** 컴퓨터에 의하여 실행되어, 청구항 1 또는 청구항 2의 방법을 수행하도록
하는 컴퓨터 프로그램.

**【청구항 4】** 컴퓨터에 의하여 판독 가능한 기록매체에 저장된 컴퓨터 프로그램으로서,
컴퓨터에 의하여 실행되어 청구항 1 또는 청구항 2의 방법을 수행하도록 하는 것을
특징으로 하는 컴퓨터 판독 가능한 기록매체.

**【청구항 5】** 자연어로 표현된 임무 요청을 외부 텍스트 도메인 특화 언어(DSL)로
변환하는 로봇 임무 기술 방법으로서,

지도 데이터로부터 노드 식별자 목록, 엣지 식별자 목록, 주행 가능 구간(hop) 목록 및
좌표를 추출하여 어휘를 구성하는 단계;

상기 어휘, 상기 DSL의 문법 레퍼런스, 및 상기 DSL에 대한 출력 규칙을 포함하는
프롬프트에 기초하여 언어 모델로부터 상기 DSL의 소스를 생성하는 단계;

상기 생성된 소스에서 마크다운 코드 울리 및 선두 서술문을 제거하는 출력 정제 단계;

상기 정제된 소스를 파싱하여 중간 표현(AST)을 생성하고, 상기 AST를 의미 규칙에
대하여 검증하는 단계;

상기 검증 결과가 거부인 경우, 상기 거부 사유를 포함하는 피드백을 상기 언어
모델에게 제공하여 재생성을 요구하는 단계로서, 상기 거부 사유는 파싱 오류의 경우
줄·열 정보를 포함하고, 상기 주행 가능 구간 판정의 경우 상기 지도가 연결하지 않는
구간에 대한 사유를 포함하는, 재생성 요구 단계; 및

상기 검증 결과가 수용인 경우, 상기 수용된 소스에 대응하는 메시지를 생성하여
제공하는 단계;

를 포함하되, 상기 파싱 및 의미 검증을 통과하지 못한 소스는 운영자에게 제공되지도
않고 기록매체에 기록되지도 않는 것을 특징으로 하는 로봇 임무 기술 방법.

### 종속항

**【청구항 6】** 청구항 5에 있어서, 상기 거부 사유에는 상기 주행 가능 구간 목록에
포함되지 않는 구간을 포함하는 경로에 대하여, 상기 구간의 시작 노드가 도달 가능한
노드들을 제시하는 문장이 포함되는 것을 특징으로 하는 로봇 임무 기술 방법.

**【청구항 7】** 청구항 5에 있어서, 상기 어휘를 구성하는 단계는 상기 지도 데이터의

## 9. 발명을 실시하기 위한 구체적인 내용

【0065】이하, 첨부 도면 및 실시예를 참조하여 본 발명을 상세히 설명한다. 다만, 이하
실시예는 참조 구현 `robotdsl`(Haskell, GHC 9.10 기반, 핵심 의존: `megaparsec`,
`aeson`, `text`, `containers`, `time`)의 실제 동작에 기초한다.

### 9.1 실시예 1 — 최소 DSL 및 자동 생성 필드

【0066】운영자가 아래와 같은 최소 소스를 작성한다.

```robotdsl
robot "acme" "AMR-001"

instant "정지" {
  action "startPause"
}
```

【0067】컴파일러는 다음과 같은 메시지를 출력한다.

```json
{"actions":[{"actionId":"startpause-1","actionType":"startPause","blockingType":"NONE"}],
 "headerId":1,"manufacturer":"acme","serialNumber":"AMR-001",
 "timestamp":"2026-11-13T12:00:00.000Z","version":"3.0.0"}
```

【0068】운영자는 `actionId`, `blockingType`(즉시액션은 자동 `NONE`), `headerId`,
`timestamp`, `version`, `manufacturer`, `serialNumber`를 일체 기입하지 않았다. 이는
발명의 핵심 효과인 "운영자는 무슨 일이 일어나야 하는지만 기술한다"는 점을 보여준다.

### 9.2 실시예 2 — 주문(order)과 세그먼트 추상화

【0069】

```robotdsl
robot "acme" "AMR-001"
map "plant-b"

order "order-pallet-1" update 0 describe "KLT palletizing run" {
  base {
    node "RK-AM" describe "rack aisle marker" at (12.5, 3.0) facing 0.0 {
      action "pick" blocking HARD describe "grab pallet" with {
        loadId = "KLT-42"
        loadType = "EPAL"
      }
    }
    edge "e-1" describe "main aisle" speed 0.8 length 14.2
    node "CHG-01" describe "conveyor A drop point" at (0.0, 0.0) facing 1.5708 {
      action "drop" blocking HARD with { loadId = "KLT-42" }
    }
  }
  horizon {
    go to "ST-07" at (7.0, 1.0) via "e-2" speed 0.5 {
      action "initPosition" describe "localise before the next pick"
    }
  }
}
```

【0070】상기 소스에서 `go to "ST-07" ... via "e-2"`는 파서에서 엣지 후속 노드로
전개되며, 하향변환 결과 `released: true`(base) 구간과 `released: false`(horizon)
구간이 구분된다. `sequenceId`는 세그먼트를 넘어 연속 증가하여 노드는 짝수, 엣지는
홀수를 갖는다. 출력 시 각 파일은 MQTT 토픽과 함께 보고된다(예:
`out/order-pallet-1.order.json  (vda5050/v3/acme/AMR-001/order)`).

### 9.3 실시예 3 — 존(zoneset)과 표준 어휘 투영

【0071】

```robotdsl
zoneset "zs-floor1" on map "plant-b" describe "Floor 1 navigation constraints" {
  zone "welding-corner" describe "welding cell, no entry" blocked {
    polygon (0, 0) (5, 0) (5, 5) (0, 5)
  }
  zone "pedestrian-zone" speed_limit 0.25 {
    polygon (20, 0) (26, 0) (26, 6) (20, 6)
  }
  zone "hazard-entry" describe "sound the beacon through the hazard area" action {
    entry { action "beaconOn" describe "start the beacon" }
    during { action "beaconOn" }
    exit { action "beaconOff" }
    polygon (28, 0) (34, 0) (34, 6) (28, 6)
  }
  zone "prefer-left-lane" priority factor 0.8 {
    polygon (36, 0) (40, 0) (40, 6) (36, 6)
  }
  zone "flow-north" directed heading 0.0 strictness restricted {
    polygon (48, 0) (52, 0) (52, 12) (48, 12)
  }
  zone "two-way-lane" bidirected heading 1.5708 strictness soft {
    polygon (54, 0) (58, 0) (58, 12) (54, 12)
  }
}
```

【0072】상기 DSL 키워드와 표준 어휘의 대응은 다음과 같다.

| DSL 키워드 | 표준 `zoneType` | 추가로 생성되는 필드 |
|---|---|---|
| `blocked` | `BLOCKED` | — |
| `line_guided` | `LINE_GUIDED` | — |
| `release` | `RELEASE` | — |
| `coordinated_replanning` | `COORDINATED_REPLANNING` | — |
| `speed_limit 0.25` | `SPEED_LIMIT` | `maximumSpeed` |
| `action` | `ACTION` | `entryActions`, `duringActions`, `exitActions` |
| `priority factor 0.8` | `PRIORITY` | `priorityFactor` |
| `penalty factor 0.9` | `PENALTY` | `penaltyFactor` |
| `directed heading 0.0 strictness restricted` | `DIRECTED` | `direction`, `limitation` |
| `bidirected heading 1.5708 strictness soft` | `BIDIRECTED` | `direction`, `limitation` |

【0073】액션 존은 스키마가 세 개의 액션 그룹과 정점을 모두 요구하므로, 비어 있어도
`entry { }`, `during { }`, `exit { }`를 기입해야 한다. 이 규칙은 의미 검증 및
프롬프트의 "쉽게 틀리는 규칙" 양쪽에 명시된다.

### 9.4 실시예 4 — 의미 검증 오류와 피드백

【0074】아래 소스는 파싱은 통과하지만 의미 검증에서 거부된다.

```robotdsl
instant "pause" {
  action "startPause" blocking HARD
}
```

【0075】산출 오류:

```
instant action 'startPause': blockingType must be NONE in VDA 5050 v3.0.0: instant actions always run in parallel with movement, so the schema's enum is only "NONE". Write the action without a blocking clause (or use `blocking NONE`). Got HARD, which is only valid on order actions.
```

【0076】또 다른 사례로, 엣지가 연속하는 주문은 다음 오류를 산출한다.

```
order 'o1' step 2: steps must alternate node, edge, node, ...; this edge 'e5' follows another edge 'e4'
```

【0077】상기 오류 메시지는 CLI 표준 오류로 출력될 뿐 아니라, 생성 루프에서
그대로(줄·열 정보 포함) 언어 모델에게 피드백되어 재생성을 유도한다.

### 9.5 실시예 5 — 자연어 생성 루프 동작

【0078】운영자가 "랙에서 팔레트를 집어 컨베이어 A로 가져다줘"라고 음성 또는 텍스트로
요청하면, 시스템은 다음과 같이 동작한다.

1. 지도로부터 어휘를 구성한다(맵 식별자, 노드 id, 엣지 id, 홉, 좌표).
2. 대상 로봇 상태를 조회한다(오프라인/주행 중/대기).
3. 프롬프트(출력 규칙 + 문법 + 어휘 + 로봇 + 11개 규칙 + 2개 few-shot)를 구성한다.
4. 언어 모델이 DSL 소스를 생성한다. few-shot 예시는 아래와 같다.

   ```
   Request: 랙에서 팔레트를 집어 컨베이어 A로 가져다줘
   Answer:
   robot "acme" "AMR-001"
   map "plant-b"
   order "order-pallet-1" {
     base {
       node "RK-AM" at (12.5, 3.0) facing 0.0 {
         action "pick" describe "grab pallet" with { loadId = "KLT-42" }
       }
       go to "CHG-01" at (0.0, 0.0) facing 1.5708 {
         action "drop" with { loadId = "KLT-42" }
       }
     }
   }
   ```

5. 출력에서 마크다운 울리와 선두 서술문을 제거한다.
6. 파싱 → 선언 주입 → 의미 검증 → 하향변환을 수행한다.
7. 주행 가능성 판정을 수행한다. 맵이 `RK-AM`을 `RK-AE`, `RK-AW`에만 연결한다면
   `RK-AM -> CONV-OUT`는 다음 사유로 거부된다:
   `there is no edge from RK-AM to CONV-OUT; from RK-AM the map connects only to RK-AE, RK-AW, so travel through those nodes`
8. 동일 사유가 피드백되어 재생성이 요구되고, 최대 3회까지 반복된다.
9. 수용된 결과만 대화 이력에 기록되고, 미리보기가 지도 위에 표시된다.

### 9.6 실시예 6 — 미리보기와 유실 구성 경고

【0079】미리보기는 지도 위에 경로를 그리고, 지도가 모르는 노드와 홉을 보고하며,
관제 게이트웨이가 버리는 구성을 경고한다. 예컨대 다음 경고가 산출될 수 있다.

- `edge 3: maximumSpeed is dropped by the fleet gateway`
- `edge 5: 2 action(s) here are dropped by the fleet gateway`
- `the fleet gateway has no zoneSet endpoint, so the 1 zone set(s) here will not reach the robot`
- `node AS-1W is visited 2 times, so the robot backtracks through it`

【0080】상기 경고는 어드바이저리(권고)이다. 미리보기는 발행하거나 기록하지 않으며,
운영자가 판단할 수 있도록 사실을 보고하는 데 그친다.

### 9.7 실시예 7 — 독립 교차 검증

【0081】출력 디렉터리에 대해 별도 구현체(Python)가 핵심 불변량을 재검사한다. 검사
항목은 필수 필드 존재, `sequenceId` 짝·홀 규칙, `blockingType` 열거형, `zoneType`별
페이로드 요구사항, `actionId` 고유성, ISO 8601 밀리초 타임스탬프 형상, v2 필드명
부재이며, 첫 위반에서 0이 아닌 종료 코드를 반환한다(참조 구현 기준 274건 검사).

### 9.8 실시예 8 — 표준/벤더 프로파일 교체

【0082】신규 표준 버전(예: 차기 v3.x)이나 신규 벤더 인터페이스에 대응할 때,
운영자는 새 프로파일(프로토콜 버전 식별자, 스키마 세트, 토픽 체계, 하향변환 규칙,
의미 규칙 세트)을 등록한다. DSL 문법, 의미 검증기, 생성 루프, 미리보기, 사용자
인터페이스는 변경되지 않는다. 이는 종래의 N×M 어댑터 유지보수를 N+M으로 줄인다.

## 10. 요약

【0084】본 발명은 복수 로봇 벤더 및 복수 로봇 통신 표준 버전이 갖는 인터페이스
이질성을, 예약어가 없는 따옴표 이름과 순서 자유 수식어를 갖는 외부 텍스트 DSL과,
표준 북키핑을 배제한 표준 중립 AST, 의미 검증 계층, 북키핑 자동 생성 하향변환
계층, 공식 스키마 검증 계층, 및 교체 가능한 표준/벤더 프로파일의 조합으로
단일화한다.

【0085】또한 자연어·음성 요청을 DSL로 변환하는 생성-검증-재시도 루프를 두되,
지도 기반 어휘 접지와 주행 가능성 판정을 결합하여 환각 식별자와 주행 불가 경로를
제거하고, 파싱·의미 검증을 통과하지 못한 출력은 운영자에게 제공되지도 않고 기록되지도
않게 한다.

【0086】이에 따라 운영자는 벤더나 표준 버전과 무관하게 단일한 평문 인터페이스로
임무를 기술할 수 있고, 표준 준수가 구조적으로 보장되며, 신규 표준·벤더 대응 비용이
크게 감소한다.

## 부록 A. 용어 정리

| 용어 | 의미 |
|---|---|
| 북키핑(bookkeeping) | 표준이 요구하나 임무 의미와 무관한 메타데이터(`headerId`, `timestamp`, `version`, `sequenceId`, `actionId`, `edgeId`, `mapId`) |
| 하향변환(lowering) | 표준 중립 중간 표현을 특정 표준의 메시지로 변환하는 단계 |
| 홉(hop) | 지도에서 한 노드에서 다른 노드로의 직접 연결(from, to) |
| 세그먼트 | `released: true`인 구간(base/route)과 `released: false`인 구간(horizon) |
| 프로파일 | 대상 표준·버전·벤더를 규정하는 교체 가능 설정(버전, 스키마 세트, 토픽 체계, 하향변환 규칙, 의미 규칙) |
| 접지(grounding) | 자연어 생성 시 실제 지도 식별자와 연결 관계에 기반하여 출력을 제약하는 것 |

## 부록 B. 참조 구현 기반 사실 관계

- 대상 표준: VDA 5050 v3.0.0(`zoneSet` 및 전체 `zoneType` 어휘 포함).
- 핵심 언어: Haskell(GHC 9.10), 핵심 의존 `aeson`, `megaparsec`, `text`,
  `containers`, `time`. 에이전트는 `warp`, `wai`, `http-conduit`를 사용하나 별도
  서브라이브러리에 격리되어 핵심 DSL은 웹 서버에 링크되지 않는다.
- 검증: 파싱 → 의미 검증 → 스키마 검증 3단계, 실패 시 파일 미기록. 독립 Python
  교차 검증 274건. 105개 단위 테스트 케이스 + 브라우저 자동화 테스트.
- CLI: `check`(파싱 + 의미 검증), `compile`(+ 하향변환 + 스키마 검증 + 출력).
- 에이전트: `--map`(파일) 또는 `--fleet`(게이트웨이 실시간 조회), 음성 입력
  (`--stt`), 브라우저 UI(빌드 단계 없음).
